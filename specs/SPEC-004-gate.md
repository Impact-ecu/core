# SPEC-004 · Verification gate and verdict taxonomy

Status: draft
Date: 2026-10-18
Revision: 1 (2026-10-18), proposed with SPEC-006 (ADR-002): `check_input` and `release` take `evidence` and `as_of`; R16 intersects the admitted set with field evidence the gate checks itself (signed, unexpired registry head; `golden_field` recomputed). A variant that fails R16 follows the existing `unknown_variant` path, so no finding, report field or vector changes. Breaking under the compatibility rules of this spec.
Revision: 2 (2026-10-19): `check_input` and `release` take `verifier: Verifier | None`, the injected Ed25519 verifier SPEC-006 R83 needs to run `evidence_admission` itself (R16); `None` makes evidence `unavailable`, so no variant is admitted for recalculation (fail-closed).
Governs: `src/core/gate/`, the construction of `InputResult` and `ReleasedImage`, the gate report, and how the gate reads the events it consumes.
Derives from: SPEC-000 §Verification gate: the only way out, §Binary kernel invariants (invariant 10), §Virtual test bench (level 1), §Data model (Event, MapDef label states), §Ingestion and analysis pipeline (step 5), §Plugin SDK per ECU family, §Golden files, §Non-functional requirements; SPEC-001 R7–R9, R40–R42, R60–R65; SPEC-002 (plugin contract, checksum references); SPEC-003 (definitions, span, units); SPEC-005 R36 (event payloads); ADR-001.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Every numbered rule (`R<n>`) is normative and MUST be cited by at least one test (`# SPEC-004 R<n>`). Rules of other specs are written `SPEC-00N R<n>`.

## 1. Problem

The gate is the only way a binary leaves Impact (SPEC-000 §Verification gate). It runs twice: on the original, to decide whether the file that came in is intact, and on the materialized image, to decide whether the file about to go out is intact and plausible. If it approves a dangerous file, or blocks a good one, trust in the product is gone (SPEC-000 §Why everyone depends on this being 100% correct, row "Virtual bench"). This spec fixes what blocks, what warns, the report format, how a user confirms a warning, and what is recorded, precisely enough that two implementations produce the same report bytes for the same inputs.

Out of scope: plugin behavior, the `VerifyReport` shape and the checksum references (SPEC-002), `MapDef` decoding, spans and units (SPEC-003), event payload shapes, the event hash chain and the provenance record (SPEC-005), the before/after datalog (SPEC-000 §Virtual test bench, level 1b: informative, never blocks), and levels 2 and 3 of the bench (cut from the MVP).

## 2. Verdicts and findings

```
Verdict  = "block" | "warn" | "no findings"
Severity = "block" | "warn" | "info"
Finding  = { rule_id, rule_version: int, severity: Severity, text: string,
             map_id: string | null, cells: list[[row, col]], axis: "x" | "y" | null,
             breakpoints: list[int], runs: list[{memory_id, offset, length}], incident: "S1" | null }
```

- **R1.** The gate's outcome is a `Verdict` carried inside a report (§6). It is never a boolean, and no API, field or text calls a verdict "pass" or "passed" (SPEC-000 §Verification gate, "Ternary verdict"). `no findings` means the gate found nothing, not that it approved the file.
- **R2.** A `Finding` names the rule that produced it, the rule's version, and where it applies: `cells` (row, column indices into the map's value grid, row 0 first), `axis` and `breakpoints` (indices `i` of axis pairs `(i, i+1)`; for `G-NONFINITE`, indices of the non-finite breakpoints), or `runs` (byte runs, SPEC-001 offsets). Fields that do not apply are `null` or empty. `text` is the rule's fixed text (§5, §9); it never embeds a cell value. `incident` is `"S1"` only where this spec says so (R24, R25, R27, R28). The core is pure (R80): it never opens an incident; a finding with `incident: "S1"` obliges the caller to open one.
- **R3.** `info` is a table severity, used for downgrades (R63). An `info` finding goes to `information` in the report and never affects the verdict.
- **R4.** The verdict of either stage is computed from the report's `findings` list only (silenced findings excluded, R61): `block` if any finding has severity `block`; else `warn` if any has severity `warn`; else `no findings`.
- **R5. What blocks.** Severity `block` is reserved for the physically impossible or structural (SPEC-000 §Verification gate): a value outside the sensor range, a non-monotonic axis, a patch in a protected region, a checksum failure or containment failure, injector duty above 100%, plus the fail-closed and integrity rules of §3 and §4, which SPEC-000 also makes blocking (input failures, kernel invariants, `verify`, dual implementation, unavailability). The complete list of `block` rules is the `block` rows of §9 and the `sensor_range` kind (R33). No other rule may block.
- **R6. What warns.** Severity `warn` is for plausibility only (SPEC-000 §Verification gate). The one exception is a signed region: `G-INPUT-SIGNED` (R13) and `G-VERIFY-SIGNED` (R26), because SPEC-000 §Plugin SDK per ECU family makes a signed region a `warn` export ("the gate exports only with `warn`"). A `verify` whose status is `signature_unverifiable` is green (SPEC-000 invariant 10, SPEC-001 R42: no region `fail` or `bypassed`, every recalculable region `ok`).
- **R7. Diff is never a rule.** No rule kind takes the original's value of a cell as an input; rules see only the release candidate (SPEC-000 §Verification gate, "Diff above threshold is not an alert rule"). The per-map diff goes into the provenance report as information (SPEC-005), never as a finding.
- **R8. Disclaimer.** Every report carries `disclaimer`, whose value is exactly: `This gate verifies file integrity and cell-by-cell plausibility. It does not verify the combination between maps, firmware behavior, or the real engine.` (SPEC-000 §Verification gate). In the canonical JSON (R40) it is the first member, and every rendering of the report (PDF, page, terminal) opens with it.

## 3. Input gate

`gate.check_input(dump, *, declared_sha256, received_sha256, project_id, plugin, conformance_report, evidence, as_of, verifier, confirmation, rule_table) -> InputResult`

`InputResult = {report, report_hash, artifact_state: "accepted" | "suspect", identification: Identification | None}`, where `identification` is the result of the gate's own `plugin.identify(dump)` call (R12). `conformance_report` is the plugin's published SPEC-002 R126 report object (R15). `received_sha256` is the SHA-256 of the file as received, computed by the consumer that read it (the core does no I/O; SPEC-001 R2 makes that hash the artifact's identity). `confirmation` is an `identification_confirmed` event (SPEC-005 R36) or `null`.

- **R9. Sealed result.** `InputResult` is immutable and constructed only by `core.gate`, with the same structural guarantee as `ReleasedImage` (SPEC-001 R8, R9): no public constructor, and import-linter forbids consumers from importing the module that builds it. Python cannot make this a hard barrier; the accepted limitation of SPEC-001 R8 applies. `gate.release` accepts only an `InputResult` (R20) and re-checks its binding to the original (R22).
- **R10.** The input gate runs the three checks of SPEC-000 §Verification gate ("Input") and reports each as tested or not tested (kinds `input_hash`, `identify`, `input_verify`, R41). Unavailability of the plugin (including its conformance report, R15) or of the rule table (which holds the confidence threshold) yields `G-UNAVAILABLE-PLUGIN` / `G-UNAVAILABLE-RULES` (fail-closed, SPEC-000 §Verification gate).
- **R11. Hash.** `declared_sha256 != received_sha256` (compared as lowercase hex, SPEC-001 R65) → `G-INPUT-HASH`, block.
- **R12. Identify.** The gate calls `identification = plugin.identify(dump)` itself and never accepts an identification from the caller (SPEC-000 §Verification gate, "the gate is a core function, not an API step someone can skip"). `identify` is pure and never raises (SPEC-002 R12, R101); an exception makes the plugin unavailable for the job (SPEC-002 R11) → `G-UNAVAILABLE-PLUGIN`, and an output that violates SPEC-002 §2.1 → `G-PLUGIN-ERROR`. The input subject records `plugin: {family, version}` and `identification_hash = sha256(JCS(identification))` (SPEC-001 R60, R65), or `null` when `identify` returned `None`, so the output gate can bind to it (R23). `identification.confidence` is an integer in thousandths, `[0, 1000]` (SPEC-002 R3), and the rule table's `identify_min_confidence` is an integer in the same unit. Identification passes when `confidence > identify_min_confidence`, or when `confirmation` confirms exactly this identification: `type` is `identification_confirmed`, `project_id` equals `project_id`, and its payload (SPEC-005 R36) has `artifact_sha256 == received_sha256`, `image_hash == image_hash(dump)` (SPEC-001 R62), `family == plugin.family`, `plugin_version == plugin.version`, and `hw_id`, `sw_id`, `checksum_variant_id` equal to `identification`'s. A confirmation that does not match is ignored. The confirmed variant is therefore the variant `verify` uses. Otherwise, including when `identify` returned `None`, → `G-INPUT-IDENTIFY`, block, and `verify` is not run (`not_tested`, reason `identify_failed`). The confirmation's `event_id` is recorded in the report subject only when it was used.
- **R13. Verify.** For a variant that is not admitted (R15) the gate does not call `verify` and the status is `not_applicable`, reason `unknown_variant` (SPEC-002 R42). Otherwise input `verify` with status `ok` → no finding; `signature_unverifiable` → `G-INPUT-SIGNED`, warn (R6). Any other status (`fail`, `bypassed`, `not_applicable` including `unknown_variant` per SPEC-002 R42, or a status this spec does not know) → `G-INPUT-VERIFY`, block, with text `input verify returned <status>`. The core's comparison of the plugin with the reference (SPEC-002 R45) runs here too: a `PluginContractError` with reason `plugin_disagreement` or an `InterpreterDivergence` → `G-DUAL-DIVERGENCE`, block, `incident: "S1"`, as in R27. A report status that differs from the core's recomputed aggregation (SPEC-002 R43, reason `r43`) or any other plugin exception or contract error → `G-PLUGIN-ERROR`, block. The input subject records `verify_status`, the status of the input verify (`not_applicable` for `unknown_variant`, `null` when verify was not run), and `signed_regions`, the regions of `kind = signed` of that verify (`[]` when verify was not run), so the output gate (R22) and provenance (SPEC-005 R14, R63) never parse a finding text.
- **R14. Suspect.** An input verdict of `block` marks the artifact `suspect` (`artifact_state = "suspect"`, else `"accepted"`). Consumers MUST NOT record patches for a `suspect` artifact (SPEC-000 §Verification gate, "blocks editing") unless every `block` finding of the input report is `G-INPUT-VERIFY` and a `suspect_ack` event (SPEC-005 R36) references the input `report_hash` (SPEC-000 §Ingestion, step 5). `G-INPUT-HASH` and `G-INPUT-IDENTIFY` cannot be acknowledged: the remedy is a new upload or an `identification_confirmed` event. The output gate re-derives this condition itself from the sealed `InputResult` (R9, R22, R23), so a consumer that skips or forges the input check still cannot export.
- **R15. Admission.** `conformance_report` is the plugin's published conformance report (SPEC-002 R126, R130). The gate computes and records its `report_hash` (SPEC-002 R127) and requires its `plugin.family` and `plugin.version` to equal the plugin's and its `verdict` to be `conformant`; a `None` report or any mismatch → `G-UNAVAILABLE-PLUGIN`. The admitted set is the `checksum_variant_id`s of its `variants` with `admitted: true` (SPEC-002 R131, R132). A variant whose `checksum_variant_id` is `null` or not in the admitted set is `unknown_variant` (ADR-001 decision 7): the gate never calls `verify` or `checksum_patches` for it, at either stage; its verify status is `not_applicable`, reason `unknown_variant` (SPEC-002 R42), which blocks (R13, R26). Both subjects record `conformance_report_hash` (SPEC-000 §Golden files, "Plugin release requires `golden_field` per variant"). The report is caller-supplied, with the same trust as the plugin object itself: nothing in `core` anchors it to the published release (accepted limitation, as SPEC-001 R8; open question 12). The admitted set is further restricted by R16.
- **R16. Field evidence.** The gate runs SPEC-006 `evidence_admission(evidence, trust, policy, as_of, verifier)` itself, with the registry trust anchor and the head policy published with the core release (SPEC-006 R60, R82) and `as_of` supplied by the caller (R80). A variant is admitted only if it is admitted by R15 **and** the result has status `current` and lists the variant with `golden_field: true` (SPEC-006 R84). `evidence: None`, an untrusted, not yet valid, expired or over-long registry head, a registry that does not match the head, or a variant below `golden_field` or with an unreviewed negative make the variant `unknown_variant`, exactly as a variant missing from the conformance report: `verify` and `checksum_patches` are not called and the run blocks through R13 and R26. The gate never takes an admission or a level from the caller; a stale registry cannot hide a revocation for longer than one head validity period (SPEC-006 R82). (ADR-002 Decision 5; SPEC-006 R81–R84)

## 4. `gate.release`

```
gate.release(u: UnverifiedImage, *, original: Dump, version: Version,
             plugin: EcuPlugin | None, conformance_report: ConformanceReport | None,
             evidence: FieldEvidence | None, as_of: Timestamp, verifier: Verifier | None,
             references: Mapping[str, RegionReference], definition: Definition,
             engine: {combustion: "SI" | "CI" | null, fuel: Fuel | null}, rule_table: RuleTable | None,
             project_id: ProjectId, input: InputResult, suspect_ack: Event | None,
             silences: list[Event]) -> ReleasedImage            # raises GateBlocked(report, report_hash)
Fuel = "gasoline" | "E27" | "E100" | "flex" | "diesel"
```

`u` is produced by `apply` (SPEC-001 §3); `plugin`, `ChecksumRegion.reference`, `RegionReference` and `conformance_report` follow SPEC-002; the gate takes no identification and no layout from the caller: it computes both from `original` (R23); `definition` is the project's `Definition` (SPEC-003 §3.6), including its `AxisDef`s; `rule_table` is a versioned table (§5); `input` is the result of `check_input` on `original`.

- **R20. Order.** `release` runs these steps in this order and records every check as tested or not tested (kinds in R41):
  1. availability (R21), which calls `plugin.identify(original)` and computes admission (R15); any failure stops here;
  2. binding (R23, kind `binding`);
  3. input state (R22, kind `input_state`);
  4. kernel invariants and protected regions (R24);
  5. checksum step (R25);
  6. `verify` on the release candidate (R26);
  7. dual implementation (R27);
  8. map rules (§5) on the release candidate;
  9. silences (R61), verdict (R4), report (§6).
  A `block` finding in step 2, 4 or 5 stops the run; the remaining steps are `not_tested` with reason `earlier_block`. Findings in steps 3, 6 and 7 do not stop steps 4 to 8.
- **R21. Fail-closed.** If `rule_table` is `None` or fails validation (R33) → `G-UNAVAILABLE-RULES`; if `plugin` is `None`, or `conformance_report` fails R15, or `plugin.identify(original)` raises → `G-UNAVAILABLE-PLUGIN`; only when the plugin is available, `conformance_report` passes R15 and the variant is admitted, the gate calls `plugin.checksums(identification)` (with the `identification` of this step, the one R23 binds), and if a recalculable region has `reference.kind` `independent` and `references` has no entry for its `id`, or has `reference.kind` `none` (which SPEC-002 makes impossible for an admitted variant) → `G-UNAVAILABLE-DUAL`; when the plugin is unavailable or the variant is not admitted, dual availability is not evaluated and only the findings of that cause are reported. An exception or `PluginContractError` (for example `bad_reference`, SPEC-002 R33) from `plugin.checksums` → `G-PLUGIN-ERROR`. All are block and all present ones are reported; the steps `binding`, `input_state`, `kernel_invariants`, `checksum_step`, `verify`, `dual_checksum` and `map_rules` are `not_tested` with reason `gate_unavailable` (SPEC-000 §Verification gate, "Fail-closed"; §Non-functional requirements, "Gate latency and failure").
- **R22. Input state.** If `input.report.verdict` is `block`, release continues only when R14's condition holds, checked here: every `block` finding of `input.report` is `G-INPUT-VERIFY`, and `suspect_ack` is an event of `project_id` with `type` `suspect_ack` whose payload (SPEC-005 R36) has `input_report_hash == input.report_hash`, `image_hash == image_hash(original)`, `artifact_sha256 == input.report.subject.received_sha256` and `verify_status == input.report.subject.verify_status` (R13). The report subject then carries `input_verify: "failed_acknowledged"` (SPEC-000 §Ingestion, step 5); otherwise `"ok"`. Without that condition → `G-INPUT-SUSPECT`, block.
- **R23. Binding.** The gate computes `identification = plugin.identify(original)` and `layout = plugin.layout(identification, original.dump_kind)` itself and validates the layout per SPEC-002 R20 (a violation → `G-PLUGIN-ERROR`), then runs the static validation of the variant's descriptors against that layout (SPEC-002 R31, R79; a static `DescriptorError` → `G-PLUGIN-ERROR`). It then requires: `image_hash(original) == version.base_image_hash`; `layout_hash(layout) == version.layout_hash`; `image_hash(apply(original, version, layout)) == image_hash(u)` (SPEC-001 R20, R62–R64); and that the input result is the one of this original, plugin and identification: `input.report_hash == sha256(JCS(input.report))`, `input.report.stage == "input"`, `input.report.subject.image_hash == image_hash(original)`, `input.report.subject.plugin` equals `{family, version}` of `plugin`, `input.report.subject.conformance_report_hash` equals the hash R15 computed, and `identification` is not `None` and `sha256(JCS(identification)) == input.report.subject.identification_hash`. Any mismatch → `G-BINDING`, block. Computing `apply(original, version, layout)` can raise a `KernelError` (SPEC-001 R72): a `ContainmentError` (a patch not inside one `calibration` region of this layout, SPEC-001 R23) → `G-PROTECTED`, block, no incident, with `runs` set to the ranges of the offending patches sorted by `(memory_id, offset)`, so the report names the region the version tried to touch; any other `KernelError` from that `apply` (precondition, overlap, shape) → `G-BINDING`. Every later step uses this `identification` and this `layout` only; a layout computed elsewhere is never trusted. This binds the report to the exact original, input check, plugin, identification, version and layout it names.
- **R24. Kernel invariants.** Using `core.kernel._internal.view` (SPEC-001 R8) and the layout of R23, the gate re-checks on `(original, u)`: every patch lies in one `calibration` region (SPEC-001 R23); bytes outside the patch ranges are unchanged (R24); the shape is preserved (R26). A patch intersecting a `protected` or `checksum` region → `G-PROTECTED`, block (SPEC-000 §Verification gate, "Output"); R23 normally reports it first, and R24 repeats the check on the unverified image as an independent assertion. Any other violation → `G-INVARIANT`, block, `incident: "S1"`: it is a kernel bug (SPEC-001 R73).
- **R25. Checksum step.** For a variant that is not admitted (R15), `checksum_patches` is never called: `checksum_step` is `not_tested` with reason `unknown_variant`, no release candidate exists, and `release_candidate_hash` is `null` (R45); the run continues only to collect findings for the report. Otherwise the gate first runs the core's own derivation for descriptor regions and `references[id].patches_region` for independent regions, whatever the plugin later does; then `q = plugin.checksum_patches(view(u), identification)`, compared with that derivation (SPEC-002 R55); then `r = apply_checksum_patches(u, q, layout)` (SPEC-001 §5). A resolution `DescriptorError` of the core derivation takes precedence over any plugin outcome, so a plugin that raises on the same file (SPEC-002 R66) yields the same finding. A `PluginContractError` with reason `plugin_disagreement` or an `InterpreterDivergence` (SPEC-002) → `G-DUAL-DIVERGENCE`, block, `incident: "S1"`. A `DescriptorError` from a resolution failure of the core derivation (SPEC-002 R66) → `G-CHECKSUM-RESOLUTION`, block, no incident: the file's coverage cannot be resolved, which is not a plugin or kernel bug. A `ContainmentError` → `G-CHECKSUM-CONTAINMENT`, block. Any other plugin error → `G-PLUGIN-ERROR`, block. The gate re-asserts SPEC-001 R41 on `(u, r)`; a violation → `G-INVARIANT`, S1. `r` is the release candidate; `image_hash(r)` is `release_candidate_hash`.
- **R26. Verify.** For a variant that is not admitted (R15) the status is `not_applicable` (reason `unknown_variant`) without calling the plugin. Otherwise `plugin.verify(view(r), identification)`, with its shape and aggregation checked by the core (SPEC-002 R8, R43). R26 maps only the status the core recomputed from the region results: `ok` → no finding; `signature_unverifiable` → `G-VERIFY-SIGNED`, warn (R6); any other status → `G-VERIFY`, block, text `checksum verify returned <status> after the checksum step`; an exception or a contract error other than `plugin_disagreement`, including `r43` (a plugin status that differs from the recomputed aggregation, SPEC-002 R43), → `G-PLUGIN-ERROR`, block. The output subject records `signed_regions` as in R13. The comparison of the plugin's region results with the reference happens once, in R27.
- **R27. Dual implementation.** For every region of `plugin.checksums(identification)` (SPEC-002 §2.2), the reference is fixed by `reference.kind`: `interpreter` → the core descriptor interpreter with its two engines (SPEC-002 §4); `independent` → `references[reference.id]`, whose `verify_region` returns only `ok` or `fail` (SPEC-002 R45); any other status from it makes the reference unavailable → `G-UNAVAILABLE-DUAL`. The gate computes the per-region `RegionResult`s of the release candidate with the reference and compares them with the plugin's exactly as SPEC-002 R45 states: `stored`, `computed` and `reason` equal, and `status` equal or the plugin's `bypassed` per SPEC-002 R44 (the checksum patches were compared in R25). Any other difference, a `PluginContractError` with reason `plugin_disagreement`, or an `InterpreterDivergence` → one `G-DUAL-DIVERGENCE` finding, block, `incident: "S1"` (SPEC-000 §Verification gate, "Dual implementation where possible … export only with both agreeing. Divergence is a plugin bug and becomes S1"). Signed regions have nothing to compare (SPEC-002 R46); a variant whose regions are all `signed` lists `dual_checksum` as `not_tested` with reason `signed_only`, and a variant that is not admitted (R15) lists it with reason `unknown_variant` (its `G-VERIFY` already blocks). A divergence found in R25 stops the run (R20), so a report carries at most one `G-DUAL-DIVERGENCE`. There is no other way for `dual_checksum` to be skipped: a missing reference is `G-UNAVAILABLE-DUAL` (R21), never `not_tested`.
- **R28. No exception escapes as a release.** Every error raised inside steps 1 to 8 becomes a block finding as stated above. A SPEC-003 R22 or R55 error (`unknown_memory`, `out_of_memory`, `unknown_base_address`) raised by `span` or `decode` for a `MapDef` → `G-DEFINITION`, block, no incident, with that `map_id` (R31): a definition that does not fit the file is not a kernel bug. Only an error the gate cannot attribute is `G-INVARIANT`, S1. The gate never returns a `ReleasedImage` because a check could not run.
- **R29. Result.** If the verdict is `block`, `release` raises `GateBlocked(report, report_hash)` and constructs nothing. Otherwise it returns a `ReleasedImage` carrying `image_hash` (= `release_candidate_hash`), the memory metadata of SPEC-001 R7, `verdict`, `report` and `report_hash`. `ReleasedImage` is immutable: no attribute can be reassigned and no method changes the verdict (SPEC-000 invariant 10). Only `core.gate` constructs it (SPEC-001 R9). Its only byte accessor is `to_dump(ack)` (R51).

## 5. Rule model

### 5.1 Values

- **R30. Exact values.** Every physical value the gate compares (cells, axis breakpoints, rule parameters) is an exact rational. Its canonical text form is `^-?(0|[1-9][0-9]*)(/[1-9][0-9]*)?$`, reduced, with denominator ≥ 2 when present and no `-0`. Float32 raw values (SPEC-000 §Data model, `MapDef.dtype`) convert to their exact dyadic rational (SPEC-003 R7). No floating-point comparison happens in the gate (SPEC-001 R70 extended to the gate). Confidence is an integer (R12). A cell or breakpoint that decodes to `non_finite` (SPEC-003 R7, R56) → `G-NONFINITE`, block: for cells, one finding listing the cells; for an axis, one finding per axis with `axis` and `breakpoints` set to the non-finite indices. A map with a non-finite breakpoint lists `axis_monotonic` as `not_tested`, reason `non_finite`.
- **R31. What is evaluated.** The gate decodes each `MapDef` of `definition` from the release candidate itself (SPEC-003 R56, resolving `shared` axes in `definition`); it never accepts caller-supplied values. A map is *edited* when `span(m, definition, original)` or `span(m, definition, r)` (SPEC-003 R30: cells and every axis however reached, inline, shared, pointer cell and pointer target) intersects a patch range of `version` in the same memory. Map rules run only on edited maps; every unedited map is `not_tested` (`kind: map_rules`, reason `not_edited`). A `MapDef` whose `span` or `decode` fails on the original or on `r` (SPEC-003 R22, R55) yields one `G-DEFINITION` finding with its `map_id` and is `not_tested` (`kind: map_rules`, reason `definition_bind`); its edited state and span are unknown, so the export blocks until the definition is fixed (fail-closed), and it contributes no span to the union below. Patch bytes covered by no `MapDef` span (the union of the spans that resolved) form maximal runs → one `G-UNMAPPED` finding, warn, with the runs sorted by `(memory_id, offset)`.

### 5.2 Rule table

```
RuleTable = { table_id, version: semver, identify_min_confidence: int, rules: list[Rule] }   # int in thousandths
Rule      = { rule_id, rule_version: int ≥ 1, kind, severity, text, params,
              key: { category, map_type: "base" | "correction" | "limit" | "flag",
                     combustion: "SI" | "CI", fuel: Fuel | null, unit } }
Kind      = "range" | "conditional_cap" | "sensor_range" | "relative_amplitude" | "smoothness"
```

- **R32. Keyed ranges.** A rule applies to a map only when its whole key matches: `category`, `map_type` and `unit` of the `MapDef` (`unit` is the canonical unit of SPEC-003 R16 after raw→physical conversion), and `combustion` and `fuel` of `engine` (SPEC-000 §Verification gate, "Keyed ranges, not single ones"). Rule tables are data, versioned, and recorded in every report by `table_id`, `version` and `hash = sha256(JCS(table))` (SPEC-000 §Bench architecture, "Level 1 rules are data, not code").
- **R33. Table validation.** A table is valid only if: `identify_min_confidence` is an integer in `[0, 1000]`; `rule_id`s are unique and match `^[a-z0-9][a-z0-9._-]{0,63}$` (the `G-` prefix is reserved for §9); every parameter other than `axis_unit` is a canonical rational (R30); `range` has `min`, `max` or both; `sensor_range` has both; `conditional_cap` has `max`, `axis_unit`, `above`; `relative_amplitude` has `neutral`, `max_deviation ≥ 0`; `smoothness` has `max_step ≥ 0`; `range`, `conditional_cap` and `sensor_range` have `map_type: base`; `relative_amplitude` has `map_type: correction`; `sensor_range` has severity `block`; every other kind has severity `warn` or `info`. An invalid table is unavailable (R21).
- **R34. Context.** A rule with `fuel: null` does not run (SPEC-000 §Verification gate, "A rule without a declared fuel does not run"): it is listed once, `not_tested` with its `rule_id`, `map_id: null`, reason `rule_without_fuel`, and `kind` `physical_range` when the rule's kind is `range`, `conditional_cap` or `sensor_range`, else the rule's own kind (`relative_amplitude`, `smoothness`). Such a rule never matches a map. When `engine.combustion` is `null`, the context reason is `combustion_not_declared`; else when `engine.fuel` is `null`, `fuel_not_declared`; with a context reason no table rule matches any map. Built-in rules (§9) do not depend on `engine`.
- **R35. Reviewed category.** Physical range and relative amplitude run only for a `MapDef` that has a reviewed category per SPEC-003 R42 (`state` `reviewed` or `golden`, and `category`, `map_type` and `unit` not null; SPEC-000 §Data model, labels). For any other edited map the gate runs only axis monotonicity and smoothness, lists `physical_range` (and, for a `correction` map, `relative_amplitude`) as `not_tested` with reason `category_not_reviewed`, and emits `G-UNREVIEWED`, warn, with the fixed text of §9 (SPEC-000 §Verification gate).
- **R36. Map type.** For a reviewed edited map: `base` runs `physical_range` (kinds `range`, `conditional_cap`, `sensor_range`, and `G-INJECTOR-DUTY`); `correction` runs only `relative_amplitude` (SPEC-000: "A correction map tests only relative amplitude") and lists `physical_range` as `not_tested`, reason `map_type_correction`; `limit` and `flag` run no range check ("flags and limiters do not test range") and list `physical_range` as `not_tested`, reason `map_type_limit` / `map_type_flag`. Smoothness and axis monotonicity run for every map type.
- **R37. Rule kinds.** Bounds are inclusive. For each matching rule, the violating cells are:
  - `range`: `v < min` or `v > max`;
  - `sensor_range`: as `range`, severity `block`;
  - `conditional_cap`: `v > max` in a cell whose coordinate on an axis with unit `axis_unit` is strictly greater than `above` (row coordinate from `y_axis`, column from `x_axis`; either matching axis suffices). If neither axis has `axis_unit`, the rule is `not_tested` with its `rule_id`, kind `physical_range`, reason `axis_unit_absent`;
  - `relative_amplitude`: `|v − neutral| > max_deviation`.
  A rule with at least one violating cell yields one finding listing all of them; a finding with severity `info` goes to `information` (R3). Every matching rule that runs is `tested` with its `rule_id`, whatever its outcome. When no rule of an applicable check kind matches (and no built-in applies), the check is `not_tested` with reason `no_rule`.
- **R38. Smoothness and the precedence of not-tested reasons.** A `smoothness` rule flags both cells of every orthogonally adjacent pair whose absolute difference exceeds `max_step` (SPEC-000: "smoothness only on maps ≥ 2×2 with non-binary values"). For each edited map the gate evaluates, in this order, and the first reason that applies is the only one recorded for that kind:
  1. `axis_monotonic`: `no_axis` if the map has no axis; else `non_finite` (R30); else tested with `rule_id` `G-AXIS-MONOTONIC` (R39).
  2. `G-UNREVIEWED` if the map has no reviewed category (R35).
  3. `smoothness`: `shape` if rows < 2 or cols < 2; else `binary` if the map has at most two distinct values; else the context reason (R34); else `no_rule` if no `smoothness` rule matches; else tested per matching rule.
  4. Without a reviewed category: `physical_range` `category_not_reviewed` (and `relative_amplitude` `category_not_reviewed` for `correction`); nothing else for this map.
  5. `map_type` other than `base`: `physical_range` `map_type_<map_type>` (R36).
  6. `correction`: `relative_amplitude`: the context reason; else `no_rule`; else tested per matching rule.
  7. `base`: `G-INJECTOR-DUTY` is tested (R39) when it applies, regardless of context; then `physical_range`: the context reason; else `no_rule` if no range-kind rule matches and `G-INJECTOR-DUTY` does not apply; else each matching range-kind rule is tested or `axis_unit_absent` (R37).
- **R39. Built-in map rules.** For every edited map, each present axis MUST be strictly monotonic over its physical breakpoints: all consecutive differences positive, or all negative. The reference direction is the sign of the first non-zero difference; `breakpoints` lists every `i` whose difference `a[i+1] − a[i]` is zero or of the other sign (all `i` if every difference is zero). A violation → `G-AXIS-MONOTONIC`, block, one finding per axis. For a reviewed `base` map with category `injector_duty` and unit `percent`, a cell `v > 100` → `G-INJECTOR-DUTY`, block (SPEC-000: "injector duty above 100%").

## 6. Report

```
GateReport = { disclaimer, findings: list[Finding], gate: {core_version, rule_table: {table_id, version, hash} | null, spec: "SPEC-004"},
               information: list[Finding], not_tested: list[{kind, rule_id | null, map_id | null, reason}],
               silenced: list[Finding + {silence_event_id}], stage: "input" | "output", subject,
               tested: list[{kind, rule_id | null, map_id | null}], verdict: Verdict }
```
Output `subject` = `{checksum_variant_id | null, conformance_report_hash | null, definition_hash, engine, input_report_hash, input_verify | null, layout_hash | null, original_image_hash, plugin: {family, version} | null, references: list[{id, version}], release_candidate_hash | null, signed_regions: list[{memory_id, name}], unverified_image_hash, version_hash}`; `definition_hash` is SPEC-003 R52 of `definition`, and `references` lists every `RegionReference` used in R25 and R27, sorted by `id` (SPEC-002 R34). Input `subject` = `{checksum_variant_id | null, confidence: int | null, conformance_report_hash | null, declared_sha256, identification_hash | null, identify_confirmation_event_id | null, image_hash, plugin: {family, version} | null, received_sha256, signed_regions: list[{memory_id, name}], verify_status: VerifyStatus | null}`. `signed_regions` is sorted by `(memory_id, name)` in both subjects (R13, R26).

- **R40. Canonical form.** The report is canonical JSON per SPEC-001 R60. Every top-level member name other than `disclaimer` MUST sort after `"disclaimer"` under JCS ordering, so that `disclaimer` is the first member (R8). Adding a top-level member that violates this is a breaking change.
- **R41. Tested and not tested.** Every check the gate ran appears in `tested` (whatever its outcome) and every check it did not run appears in `not_tested` with a reason from this spec. The integrity kinds are `binding`, `input_state`, `kernel_invariants`, `checksum_step`, `verify`, `dual_checksum` (output) and `input_hash`, `identify`, `input_verify` (input); the map kinds are `axis_monotonic`, `smoothness`, `physical_range`, `relative_amplitude`, `map_rules` (SPEC-000 §"Done" criteria, Gate: "the report always lists what was tested and what was not").
- **R42. Order.** `findings`, `information` and `silenced` are sorted by `(rule_id, map_id, axis)`; `tested` by `(kind, map_id, rule_id)`; `not_tested` by `(kind, map_id, rule_id, reason)`; `null` sorts as the empty string; `cells` by `(row, col)`; `breakpoints` ascending. Identifiers are ASCII, so code-point and JCS orders agree.
- **R43. Hashes.** `report_hash = sha256(JCS(report))`; `finding_id = sha256(JCS(finding))`. Both are lowercase hex (SPEC-001 R65).
- **R44. Provenance link.** Every export's provenance carries the report hash as `gate_report_hash`, the `verdict` and, for `warn`, the `alert_ack` event reference (SPEC-000 invariant 12; record format in SPEC-005 §3). The report is also stored as `Artifact{report}` linked to the version (SPEC-000 §Bench architecture).
- **R45. Subject of a short run.** A subject field whose producing step did not run, or stopped with a block before producing its value, is `null`; the report is still complete and canonical (R29, R40). Producing steps (R20, R10): `plugin`, `conformance_report_hash` and `checksum_variant_id` come from availability (R21; `plugin` is `null` when `plugin` is `None`, the other two when `G-UNAVAILABLE-PLUGIN` is reported, and `checksum_variant_id` also when the identification has none); `layout_hash` from binding (R23); `input_verify` from input state (R22); `release_candidate_hash` from the checksum step (R25). `definition_hash`, `engine`, `input_report_hash`, `original_image_hash`, `unverified_image_hash` and `version_hash` describe caller inputs and are always set. `references` and `signed_regions` are `[]`, not `null`, when R25/R27 or R26 did not run. In the input subject the same rule applies: `plugin` is `null` when `plugin` is `None`, and `identification_hash`, `checksum_variant_id`, `confidence`, `conformance_report_hash` and `verify_status` are `null` when the step of R12, R15 or R13 that produces them did not run. Two implementations that stop at the same step therefore produce the same subject bytes (§1, R80).

## 7. Confirming a warning

- **R50. alert_ack.** A `warn` export requires an `Event` of type `alert_ack` (SPEC-000 invariant 10) whose payload shape is SPEC-005 R36's: `image_hash_release` is `ReleasedImage.image_hash`; `gate_report_hash` is the report's `report_hash`; `warnings` lists, in report order, `{finding_id, rule_id, text}` for every `warn` finding in `findings` (SPEC-000: "explicit confirmation recorded in an event with the warning text"); `presented_ms` and `confirmed_ms` are the consumer's clock, in integer milliseconds since the Unix epoch, when the warnings were shown and confirmed (used only by R62).
- **R51. to_dump.** `ReleasedImage.to_dump(ack)` returns the `Dump` only when R52 authorizes it; otherwise it raises `ExportRefused(reason)`. Every consumer writes output bytes only from `to_dump` (SPEC-001 R8).
- **R52. Authorization.** Checked in this order: verdict `no findings` with `ack` not `null` → `unexpected_ack`; verdict `no findings` with `ack` `null` → authorized; verdict `warn` with `ack` `null` → `ack_required`; a payload not of the SPEC-005 R36 shape, or `presented_ms > confirmed_ms` → `bad_payload`; `image_hash_release` differs → `image_mismatch`; `gate_report_hash` differs → `report_mismatch`; the list of `(finding_id, rule_id)` of `warnings` differs → `findings_mismatch`; the list of `text` differs → `text_mismatch`; else authorized.
- **R53. Event fields.** The gate reads, from each event it receives, `event_id`, `project_id`, `type` and `payload` (SPEC-000 §Data model, Event). Payload shapes are owned by SPEC-005 R36 (`identification_confirmed`, `suspect_ack`, `alert_ack`, `rule_silence`); this spec only states how the gate uses them (R12, R22, R50, R60). Recording, `actor`, `ts`, `prev_hash` and `hash` belong to SPEC-005. An event whose `project_id` differs from the project being released is ignored.

## 8. Silencing and alert fatigue

- **R60. Silence.** A tenant silences a rule per project with a `rule_silence` event (SPEC-005 R36) whose `justification_commitment` is not null (SPEC-000 §Verification gate, "A tenant can silence a rule per project with a recorded justification"). The justification text lives outside the chain as a SPEC-005 R82 commitment, so the gate never sees it; the consumer MUST NOT create a silence with an empty justification. A silence with `justification_commitment: null` has no effect.
- **R61. Effect.** A silence applies only to table rules with severity `warn`: their findings move from `findings` to `silenced`, with the smallest matching `silence_event_id`, and no longer count for the verdict or the ack (R4, R50). Silences never apply to `block` findings or to built-in rules (`G-*`).
- **R62. Fatigue metric.** For each `(family, rule_id)`, over a set of alert records `{family, rule_id, latency_ms | null, map_changed}`, one per `warn` finding shown: `quick_confirms` counts records with `latency_ms` not null, `latency_ms < 5000` and `map_changed` false; `fraction = quick_confirms / alerts` as an exact rational (SPEC-000 §Verification gate, "the fraction of alerts confirmed in under 5 s without changing the map"). `latency_ms` is the ack payload's `confirmed_ms − presented_ms` (SPEC-005 R36), or `null` if the finding was never acknowledged; `map_changed` is true when a later version of the project changes a byte of the finding's map before the next export. Records are built outside the core; the metric function is pure.
- **R63. Downgrade.** A rule with `fraction > 1/2` for a family is downgraded to severity `info` in a new rule-table version and enters review (SPEC-000: "a rule above 50% on this fraction, per family, is downgraded to informational and reviewed"). There is no global alert-rate target.
- **R64. No adaptation at runtime.** The gate never reads fatigue data, never changes a severity itself, and produces the same report for the same inputs and table version. A downgrade exists only as a table version.

## 10. Purity, determinism and errors

- **R81.** `core.gate` imports `core.kernel` (including `_internal`, SPEC-001 R8), `core.provenance` (to build and assert the export record, SPEC-005 R10, R92), `core.plugins` (the contract and the descriptor interpreter) and `core.definitions`; nothing below the gate imports it (SPEC-001 R9; layer order of SPEC-000 §Four layers).
- **R82.** `GateBlocked`, `ExportRefused` and every gate error carry the report or a stable machine `reason` (the reasons named in this spec). R22–R25, R29 and R52 are also runtime assertions in their owning functions (SPEC-001 R73).

## 11. Test vectors

`specs/vectors/spec-004/vectors.json` is produced by `generate.py` in the same directory. Neither script uses the core.
- **JCS:** the third-party `rfc8785` package, pinned in `requirements.txt`; the version used is recorded in the `generator` block. **SHA-256:** `hashlib`.
- **Values:** every physical value is an exact rational in the R30 string form, or the token `non_finite`; confidence and threshold are integers in thousandths; no float appears in any input or output.
- **Expected results** are hand-written per case in `generate.py` (findings, cells, tested and not-tested entries); the generator only sorts them (R42), assembles the report and hashes it. It never evaluates a rule.
- **Cross-check:** `crosscheck.py` is a second, independent, stdlib-only implementation: its own canonicalization, integer cross-multiplication instead of `fractions`, and a rule evaluator that walks rules first and maps second. It recomputes every table hash, report, `report_hash`, `finding_id`, verdict, authorization result and fatigue result, checks that `disclaimer` is the first canonical member and is verbatim in SPEC-000, checks every `G-*` finding's text against the §9 table of this file, and exits non-zero on any disagreement.
- Maps enter the vectors already decoded (R31's decoding and spans are SPEC-003's); `edited` and unmapped runs are given as inputs; integrity outcomes of steps 2–7 (binding, including a containment failure with its runs, input state, `verify` status, checksum resolution, dual result, plugin and reference availability) are given as inputs; the `identification` stands for the plugin's `identify` result and the admitted set for the conformance report intersected with the field-evidence admission (R15, R16; SPEC-006 vectors cover R16's inputs), from which both scripts derive `unknown_variant` and `identification_hash`; a map's `bind_error` stands for a SPEC-003 R22/R55 error.
- Category `test_synthetic` and its units exist only in the vectors, to exercise rule kinds for which SPEC-000 gives no values (R70). They are not ranges.

## 12. Compatibility

Changing §2 semantics, R20 order, any built-in rule or text, rule-kind semantics (R37–R39), the report schema or ordering (§6), the ack authorization (§7), or the fatigue metric (R62) is breaking: a SPEC-004 revision in a `foundation-change` PR and a **major** version of `core` (SPEC-000 §Core engineering practices, Versioning). Changing an event payload the gate reads is a SPEC-005 change (SPEC-005 §13) and breaking here too. A rule table is data with its own semver: any change that alters any report for any corpus input is a major table version, detected by running the corpus on both versions (SPEC-000 §CI pipeline, automated semver rule). Adding a reason string or an optional API is minor. Vectors change only together with the rule they test. Gate-quality targets (zero `no findings` on negative regression cases; false block below 1% of corpus exports; under 5 s per export, SPEC-000 §Non-functional requirements) are measured on the corpus, outside public CI.

4. **Which maps are evaluated.** R31 runs map rules on edited maps only, so a stock map outside a seed range never blocks or warns. SPEC-000 does not say whether unedited maps are tested.
5. **Where engine data is declared.** Where `engine.combustion` and `engine.fuel` are declared (project, definition) is not specified. (Category and unit identifiers are SPEC-003 R16 and R18; `unknown_variant` is `not_applicable` per SPEC-002 R42, which R13 and R26 block.)

The `deg_crank` sign convention is SPEC-003 open question 8 and blocks publication of the seed table (R70).
7. **Flex fuel.** "flex by ethanol axis": whether flex rules are evaluated per cell along an ethanol axis is undefined; flex has no rules.
8. **Fatigue sample size.** R63 downgrades on one alert (vector F3). SPEC-000 gives no minimum number of alerts per rule and family.
9. **Silencing scope.** R61 forbids silencing built-in warns (`G-UNREVIEWED`, `G-UNMAPPED`, `G-VERIFY-SIGNED`) and silences per `rule_id` across rule versions. SPEC-000 says only "a rule per project".
10. **Tenant-edited tables.** SPEC-000 §Virtual test bench makes level-1 rules "editable by an advanced tenant". R33 prevents a table from adding blocks other than `sensor_range` or turning built-ins off, but a tenant table can loosen warns. Whether tenant tables are allowed in the MVP, and how they appear in provenance, is open.
11. **Received hash.** The core cannot recompute `received_sha256` (it never sees the file). Should `check_input` instead take the raw bytes of a single-memory file and hash them itself?
12. **Anchor for the conformance report (decision for Luiz).** R15 computes and records `conformance_report_hash`, but the report object is caller-supplied, so a consumer can pass a report that marks a variant `admitted`. An anchor (for example a hash pinned in the plugin package metadata and read through `plugin`, or a signature of the release workflow) would close this; none is specified.
